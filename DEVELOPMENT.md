# Development

The project is a Dockerized Django/DRF backend and Angular 22 frontend. The
development image includes Node.js, Angular CLI, Python tooling, and WireGuard
utilities. Use the supported development shell for executable validation.

## Architecture

- **Frontend:** Angular 22 responsive SPA.
- **Backend:** Django and Django REST Framework.
- **Database:** SQLite at `/data/wg_ui_plus.db`.
- **Serving:** Django serves the Angular application and static files using
  `django-spa` and WhiteNoise.
- **WireGuard:** Generated configuration is stored at
  `/config/wireguard/wg0.conf`.
- **Images:** The multi-stage `Dockerfile` provides development, Angular build,
  and Alpine-based production stages.

## Development shell

From the repository root, build the local images and start the shell:

```bash
./build-docker-images.sh
./run-dev-shell.sh
```

The launch script assumes the `wg-ui-plus-dev` image already exists; it does not
build or pull the image. If it is not available, build the local images first
and then run `./run-dev-shell.sh`; do not run validation in the host environment.
The repository is mounted at
`/wg-ui-plus` in that shell, and the Django project is also available at
`/app/api_project`.

The launch scripts use `docker-env-dev.txt` when it exists, otherwise
`docker-env.txt`. This applies to `run-dev-shell.sh`, `run-ng-build-watch.sh`,
and `run-app-dev.sh`. The image-build script does not use those environment
files.

## Frontend workflow

Inside the shell:

```bash
cd /wg-ui-plus/src/clientapp
npm install
ng build --configuration production --prerender=false --deploy-url=/ --base-href=/
ng test
```

The application is served by Django as a SPA, so retain `--prerender=false` and
the root deploy/base URLs for a production-like build. The repository currently
has no Angular `*.spec.ts` files, but the Karma test target is configured.

For a live development loop, use two terminals from the repository root:

```bash
./run-ng-build-watch.sh
./run-app-dev.sh
```

The development application is available at `http://localhost:8000`; the live
development container exposes WireGuard UDP on host port `1196`.

## Backend workflow

Run backend tests in the shell from `/app/api_project`:

```bash
cd /app/api_project
../scripts/run-tests.sh
```

The script runs pytest doctests, writes JUnit output under `junit/`, and emits
coverage reports. Focused tests can be run with pytest, for example:

```bash
pytest api_app/test_mcp.py
```

Useful Django commands include:

```bash
./manage.py check
./manage.py migrate
./manage.py makemigrations
```

Do not hand-edit migration files; review migrations generated by Django before
including them. The repository's broad coverage command references a stale
`--cov=com` target, so use the checked-in test script unless separately fixing
that configuration.

## Source layout and contribution notes

- `src/api_project/` contains Django, models, serializers, viewsets, WireGuard
  helpers, MCP integration, migrations, and management commands.
- `src/clientapp/src/app/` contains Angular components, routes, services, and
  shared Material modules.
- `scripts/` contains container startup, watch-build, test, and monitoring
  scripts.
- `Dockerfile` is the source of truth for development and production images.

Keep changes focused, preserve the peer/peer group/target terminology, and do
not add generated `dist/`, Angular cache, `node_modules/`, runtime `data/`, or
`config/` state to a change. Before submitting work, inspect `git diff` and run
the smallest relevant validation available in the development shell.
